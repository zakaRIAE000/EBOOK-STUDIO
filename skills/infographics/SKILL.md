# Infographics

## Doctrine (R4 — non-negotiable)

Diagrams are **deterministic SVG only**. Never image-gen for a process flow,
a comparison, a timeline, a pyramid, a decision matrix, or anything else that
represents *structured information*. Higgsfield / image-gen is reserved for
covers and ambient illustrations (mood, texture, atmosphere) — never for
anything a reader needs to read accurately. A diagram generated by a
diffusion model can mislabel a step, invent a number, or misrender text; a
diagram built from data is exactly as correct as the data it was given.

Every pattern below is **parameterized only by `tokens.css` variables** —
zero hardcoded colors or fonts (R7). And every pattern uses real `<text>`
elements for labels, never rasterized/baked-in text — SVG `<text>` is
selectable, accessible text, so it satisfies R5 exactly like body copy does.

**Critical technical detail:** set every color via the `style` attribute
(`style="fill:var(--color-accent)"`), never the bare presentation attribute
(`fill="var(--color-accent)"`). SVG presentation attributes don't reliably
resolve CSS custom properties across renderers; `style` is CSS and always
does. These are inline `<svg>` elements embedded directly in the chapter's
HTML (not standalone files loaded via `<img>`) — that's what lets them
inherit `var(--color-*)` from the page's cascade in the first place. If a
diagram ever needs to be saved as a standalone `.svg` file for reuse outside
this pipeline, the token values have to be inlined as literal computed
colors at that point, since a standalone file has no ancestor to inherit
`var()` from.

**ViewBox, not fixed pixels.** `figure.figure` in `base.css` already forces
`width: 100%; height: auto` on any `svg` inside it, so the `viewBox`'s aspect
ratio is what actually determines the printed proportions — pick a
`viewBox` with a sane, deliberate aspect ratio for the pattern (wide for a
horizontal flow, taller for a pyramid) and never set a fixed pixel
`width`/`height` on the root `<svg>`. Because it's a vector, it stays crisp
at any print resolution — SVG figures are exempt from the QC ink/DPI checks
that apply to raster images (`src/qc/checks/image-dpi.ts`).

Wrap every diagram in the standard frame:

```html
<figure class="figure">
  <svg viewBox="0 0 W H" xmlns="http://www.w3.org/2000/svg" role="img" aria-label="…">
    <!-- pattern content -->
  </svg>
  <figcaption>…</figcaption>
</figure>
```

## 2. Traffic light (3 states)

**When to use:** a single verdict rendered as stop / caution / go — a risk
check, a readiness gate, a "should you do this" decision.

**Data shape:** `{ active: 'stop' | 'caution' | 'go', label }`.

There's no dedicated red/amber/green token in `tokens.css` — reuse the
semantic colors that already exist for exactly this purpose:
`--color-callout-warning-border` (stop), `--color-accent` (caution),
`--color-callout-tip-border` (go). The inactive lamps stay outlined at low
opacity; the active one is filled solid.

```html
<svg viewBox="0 0 300 420" xmlns="http://www.w3.org/2000/svg" role="img" aria-label="Traffic light: caution">
  <rect x="70" y="10" width="160" height="400" rx="24" style="fill:var(--color-bg-alt);stroke:var(--color-border)" stroke-width="2"/>
  <!-- Stop lamp -->
  <circle cx="150" cy="90" r="45" style="fill:var(--color-callout-warning-border)" fill-opacity="0.18"/>
  <!-- Caution lamp — active in this example -->
  <circle cx="150" cy="210" r="45" style="fill:var(--color-accent)" fill-opacity="1"/>
  <text x="150" y="330" text-anchor="middle" style="fill:var(--color-heading);font-family:var(--font-heading);font-weight:var(--weight-heading)" font-size="20">Proceed with caution</text>
  <!-- Go lamp -->
  <circle cx="150" cy="330" r="45" style="fill:var(--color-callout-tip-border)" fill-opacity="0.18"/>
</svg>
```

To render a "stop" or "go" verdict instead, swap which circle gets
`fill-opacity="1"` and which two drop to `0.18`, and move the label text
group to sit beside the active lamp.

## 3. Side-by-side comparison

**When to use:** contrasting exactly two things point by point (DIY vs.
done-for-you, old way vs. new way) where each point is short enough to sit
in one or two lines — anything longer belongs in the HTML
`comparison-table.html` component instead, which supports real wrapping
prose.

**Data shape:** `{ leftHeader, rightHeader, rows: [{ left, right }] }`, 3–5 rows.

```html
<svg viewBox="0 0 900 420" xmlns="http://www.w3.org/2000/svg" role="img" aria-label="Comparison">
  <line x1="450" y1="20" x2="450" y2="400" style="stroke:var(--color-border)" stroke-width="1.5"/>
```

## 5. Before/after split

**When to use:** showing the state change the method produces. **R3
caution:** every before/after claim here must trace back to something the
source text actually says — this pattern is a natural place to accidentally
invent a rosier "after" than the source supports. If the source doesn't
describe a concrete after-state, don't manufacture one just to fill the
panel.

**Data shape:** `{ beforeLabel, beforeItems: string[], afterLabel, afterItems: string[] }`.

```html
<svg viewBox="0 0 900 360" xmlns="http://www.w3.org/2000/svg" role="img" aria-label="Before and after">
  <rect x="0" y="0" width="450" height="360" style="fill:var(--color-bg-alt)"/>
  <rect x="450" y="0" width="450" height="360" style="fill:var(--color-bg)"/>
  <line x1="450" y1="0" x2="450" y2="360" style="stroke:var(--color-border)" stroke-width="2"/>
  <text x="225" y="45" text-anchor="middle" style="fill:var(--color-text-muted);font-family:var(--font-heading);font-weight:var(--weight-heading)" font-size="18" letter-spacing="0.05em">BEFORE</text>
  <text x="675" y="45" text-anchor="middle" style="fill:var(--color-accent);font-family:var(--font-heading);font-weight:var(--weight-heading)" font-size="18" letter-spacing="0.05em">AFTER</text>
  <!-- One <text> per bullet; x offset keeps a bullet glyph + text pair inside its half -->
  <text x="60" y="110" style="fill:var(--color-text-muted);font-family:var(--font-body)" font-size="15">— Scattered notes, no system</text>
  <text x="60" y="160" style="fill:var(--color-text-muted);font-family:var(--font-body)" font-size="15">— Redone from scratch each time</text>

</svg>
```

## 6. Pyramid (3–5 levels)

**When to use:** a hierarchy — foundational-to-advanced skill levels,
priority tiers, a "build this before that" structure.

**Data shape:** `{ levels: [{ label }] }`, ordered bottom (foundation) to

## 7. Decision table (criteria × options)

**When to use:** a matrix verdict — which of several options satisfies
which of several criteria, at a glance. This is distinct from the HTML
`comparison-table.html` component (real prose table, ≤4 columns, full
sentences): the decision table is a compact grid of check/x marks, not
paragraphs.

**Data shape:** `{ criteria: string[], options: string[], matrix: ('yes'|'no'|'partial')[][] }`
— `matrix[criterionIndex][optionIndex]`.

```html
<svg viewBox="0 0 800 320" xmlns="http://www.w3.org/2000/svg" role="img" aria-label="Decision matrix">
```
